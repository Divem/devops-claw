## Context

当前实例管理页面（`InstanceList.vue` 管理后台）的操作流程中，用户点击"更多"→"重启"、"停止"或"强制删除"会立即触发相应请求。这些是高风险操作，可能导致服务中断或数据丢失，需要用户明确确认。

现有删除操作已有 `DeleteConfirm.vue` 组件作为参考，采用 naive-ui 的 Modal + Button 实现，风格统一。

## Goals / Non-Goals

**Goals:**
- 为重启、停止、强制删除操作添加视觉明显的二次确认弹框
- 弹框显示被操作实例的名称，防止误操作其他实例
- 强制删除需要用户输入实例名称进行二次验证
- 保持与现有删除确认弹框一致的 UI 风格
- 零延迟响应用户操作，不增加等待时间

**Non-Goals:**
- 修改后端 API 或操作逻辑
- 添加额外的权限检查（前端层）
- 实现撤销功能
- 修改启动操作的行为

## Decisions

### 弹框触发位置
**选择**: 在 `InstanceList.vue` 中拦截 `action` 事件，根据 `action` 类型显示对应确认弹框。
**理由**: 
- `InstanceTable.vue` 保持纯展示组件，不关心业务逻辑
- 集中处理确认逻辑便于维护
- 与现有删除确认的模式一致

### 组件设计
**选择**: 创建独立的弹框组件：
- `RestartConfirmModal.vue` - 重启确认
- `StopConfirmModal.vue` - 停止确认  
- `DeleteInstanceConfirmModal.vue` - 强制删除确认（带名称验证）

**理由**:
- 与 `DeleteConfirm.vue` 模式一致，便于统一维护
- 组件单一职责，便于复用和测试
- Props/Emits 接口清晰：`show`, `instanceName` / `confirm`, `cancel`
- 各操作使用独立组件，文案和按钮类型可灵活配置
- 删除确认需要输入验证，与其他确认弹框行为不同

### 删除确认的特殊处理
**选择**: 强制删除弹框要求用户输入实例名称进行验证
**理由**:
- 删除是破坏性最大的操作，需要最高级别的确认
- 输入验证可以防止误点击确认按钮
- 用户必须明确知道自己在删除哪个实例
- 弹框关闭时（取消或确认后）自动清空输入

### 状态管理
**选择**: 使用本地状态（`ref`）管理弹框显示状态和待操作实例信息
**理由**:
- 无需全局状态，逻辑简单
- 避免污染 Pinia store
- 弹框生命周期与确认操作强绑定

## Risks / Trade-offs

| 风险 | 缓解措施 |
|------|----------|
| 用户双击"更多"菜单导致意外操作 | 弹框显示后屏蔽背景交互，必须明确选择确认或取消 |
| 实例名称过长导致弹框布局错乱 | 限制实例名称显示长度，添加 `text-overflow: ellipsis` |
| 与删除确认弹框风格不一致 | 复用 DeleteConfirm 的 CSS 变量和间距规范 |
| 用户忘记实例名称无法删除 | 弹框中明确显示实例名称供用户复制 |

## Migration Plan

1. **开发**: 创建确认弹框组件
2. **集成**: 在 `InstanceList.vue` 中导入并绑定事件
3. **测试**: 验证确认/取消/关闭弹框的各种交互路径
4. **部署**: 常规前端部署，无数据迁移或回滚需求
