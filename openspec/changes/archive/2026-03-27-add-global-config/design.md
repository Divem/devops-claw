## Context

管理后台（`/admin`）当前有三个页面：仪表盘、实例管理、审批管理，通过 `AdminLayout.vue` 侧边栏导航。实例管理维护 50+ 台云端电脑的基本信息（IP、状态、飞书连接），但缺少统一配置模型和 Memory 参数的能力。

现有项目级配置（`/projects/:id/admin` → `ConfigCodeMode.vue`）使用代码编辑器直接编辑 `openclaw.json`，通过 `useConfigStore` 管理状态。全局配置与之完全独立。

后端 API 目前全部为 mock 状态，全局配置功能初期同样使用 mock 数据。

## Goals / Non-Goals

**Goals:**
- 管理员可在 `/admin/global-config` 集中编辑模型和 Memory 配置
- 支持三种生效策略（强制/条件/下次启动）和四种应用范围（全部/运行中/已停止/指定实例）
- 发布后实例展示配置同步状态
- 与现有项目级配置完全隔离

**Non-Goals:**
- 不做配置版本管理和回滚
- 不做实例级配置覆盖（override）功能——条件生效策略预留 UI 入口但 MVP 后端统一按无覆盖处理
- 不做标签体系——MVP 使用预设筛选（全部/运行中/已停止）+ 手动勾选
- 不做配置对比（全局 vs 实例）
- 不做实例端的配置接收与热加载——仅管理后台前端

## Decisions

### 1. 全局配置独立于 openclaw.json

**选择**: 全局配置作为独立数据实体，不读写实例的 `openclaw.json`。

**理由**: 探索阶段已明确两者完全独立。模型和 Memory 配置由平台统一管控，不属于实例级项目配置范畴。

**替代方案**: 全局配置作为 openclaw.json 的模板注入——放弃，因为耦合度太高，修改全局配置会影响实例的其他配置项。

### 2. Store 设计：独立的 useGlobalConfigStore

**选择**: 新建 `src/stores/globalConfig.ts`，不扩展现有 `useConfigStore`。

**理由**: `useConfigStore` 职责是单文件读写（代码编辑器模式），数据结构和交互模式与全局配置完全不同。合并会导致 store 膨胀和职责混乱。

### 3. 应用范围 MVP 方案：预设筛选 + 手动勾选

**选择**: 提供「全部实例 / 仅运行中 / 仅已停止 / 指定实例」四种范围选择。指定实例模式下提供搜索和多选能力。

**理由**: 50+ 实例规模下，按状态筛选已能覆盖大部分批量操作场景。手动勾选满足精细化需求。标签体系留作 V2。

### 4. 已停止实例自动降级

**选择**: 当生效策略为「强制生效」或「条件生效」且选中实例包含已停止状态时，已停止实例自动降级为「下次启动生效」，在 UI 上显示警告提示，不阻止发布。

**理由**: 不打断管理员操作流程，同时保证信息透明。

### 5. 条件生效 MVP 实现

**选择**: UI 提供三种策略选项，但 MVP 后端统一按「立即推给无覆盖的实例」处理。由于当前无实例级 override 机制，条件生效在 MVP 阶段效果等同于强制生效。

**理由**: 提前预留 UI 入口避免后期改版，但降低 MVP 后端复杂度。

### 6. API Key 展示策略

**选择**: API Key 输入框使用密码模式（`type: password`），已保存的 Key 仅展示掩码（前 6 后 4），提供独立的「更新」按钮。

**理由**: 安全性要求，即使前端 mock 也应建立正确的交互模式。

## Risks / Trade-offs

- **[后端 API 全部 mock]** → 前端实现完成后需对接真实后端，数据结构可能在对接时调整。使用 TypeScript 接口约束降低风险。
- **[条件生效 MVP 简化]** → 用户选择「条件生效」后可能困惑为何效果与「强制生效」相同。在 UI 上以 tooltip 说明当前行为。
- **[无版本回滚]** → 误操作后无法一键恢复。通过发布前的确认弹框降低误操作概率。
- **[50+ 实例手动勾选性能]** → 实例选择列表需支持虚拟滚动或分页加载。MVP 使用 NSelect 的虚拟列表能力。
