# PRD 撰写指南

> 产品需求文档（Product Requirements Document）是产品经理与开发、设计团队沟通的核心文档，是项目顺利推进的基础保障。
> 
> **本指南以 DevOps 产品为例，提供可直接落地的写作规范和示例。**
> 产品需求文档（Product Requirements Document）是产品经理与开发、设计团队沟通的核心文档，是项目顺利推进的基础保障。

---

## 一、PRD 的作用与价值

### 1.1 核心读者群体

PRD 文档主要服务于以下角色：

**写给开发团队**
- 在需求评审会和开发计划会议之外，提供详细的功能说明，帮助开发全面准确理解需求
- 当产品不在公司时，开发可快速查阅需求定义，无需反复确认
- 为开发同学提供原型、设计稿之外的功能细节补充

**写给设计团队**
- 当原型质量不足时，设计师可通过 PRD 对照功能说明和文案要求

**写给团队新成员**
- 帮助新加入的开发或产品同学快速了解产品功能定义

**写给产品经理自己**
- 当页面功能存在多重解释时，可通过 PRD 回顾功能定义
- 作为历史记录，便于产品复盘和迭代优化

**写给所有团队成员**
- 提供完整的变更和澄清记录追踪
- 作为版本上线内容与计划内容对比的依据
- 充当统一的功能和物料查询入口（字典角色）

### 1.2 核心作用

- **补充说明**：补充原型和设计稿上不方便表达的内容，如全局规则、计算公式、多条件 Case、异常情况、特例情况等
- **内容集合**：作为版本的内容集合中心，所有相关方可通过 PRD 获取需要的信息，包括版本目标、功能、变更记录、澄清记录、原型、设计稿和详细功能规则定义

## 二、PRD 撰写原则

### 2.1 质量规范

PRD 文档必须满足以下标准：

| 维度 | 要求 | DevOps 产品示例 |
|------|------|-----------------|
| **内容完整** | 覆盖所有功能点，无遗漏 | ✅ 好：明确列出 CI/CD 流水线的 12 个阶段配置项<br>❌ 差：仅写"支持多种部署方式" |
| **功能明确** | 每个功能的定义清晰，无歧义 | ✅ 好："制品仓库保留策略：最近 30 个成功构建版本 + 最近 5 个失败版本"<br>❌ 差："保留适量构建版本" |
| **风格统一** | 文档风格一致，阅读体验良好 | 统一使用：先写功能说明 → 再写操作步骤 → 最后写预期结果 |
| **术语一致** | 术语使用统一，避免同一概念多种表述 | 统一使用"流水线"，不混用"Pipeline""工作流""任务流" |
| **语句通顺** | 表达清晰，易于理解 | ✅ 好："当代码推送到 release 分支时，自动触发部署"
| **逻辑严谨** | 功能逻辑严密，无漏洞 | 考虑边界：仓库为空时、构建失败时、并发触发时的处理逻辑 |
| **层次分明** | 结构清晰，层次分明 | 按应用 → 环境 → 流水线 → 任务 的四层结构组织 |
| **格式美观** | 排版整齐，便于阅读和查找 | 使用表格呈现环境配置参数，代码块展示 YAML 配置 |
| **易于检查** | 便于团队成员检查和核对 | 提供检查清单（Checklist），如"□ 环境变量已配置 □ 通知渠道已设置" |

> 注意：文档通常是供用户查找某个内容或快速浏览使用，因此**结构和导航**非常重要。

## 三、PRD 内容清单

一个完整的 PRD 应包含以下模块：

### 3.1 基础信息

| 序号 | 内容项 | 说明 | 重要性 |
|------|--------|------|--------|
| 1 | **版本信息** | 作者、时间、版本号等基础信息 | 必须 |
| 2 | **变更记录** | 需求变更历史记录 | 必须 |
| 3 | **澄清记录** | 需求澄清记录，帮助后期改进 PRD | 建议 |

### 3.2 业务背景

| 序号 | 内容项 | 说明 | 重要性 |
|------|--------|------|--------|
| 4 | **用户故事** | 了解本期功能的背景和用户使用场景 | 必须 |
| 5 | **角色定义** | 使用功能的角色说明 | 必须 |
| 6 | **功能价值** | 对产品目标和用户价值的作用说明 | 必须 |
| 7 | **功能范围** | 本期迭代涉及的所有功能点清单 | 必须 |

### 3.3 设计资源

| 序号 | 内容项 | 说明 | 重要性 |
|------|--------|------|--------|
| 8 | **原型稿** | 原型访问链接 | 必须 |
| 9 | **设计稿** | 设计稿访问链接 | 必须 |
| 10 | **业务流程图** | 参与角色的业务流转过程 | 建议 |
| 11 | **页面流程** | 用户完成业务流程需要跳转的页面 | 建议 |
| 12 | **操作流程** | 用户完成目标的逐步操作说明 | 建议 |

### 3.4 功能详细描述

| 序号 | 内容项 | 说明 | DevOps 示例 | 重要性 |
|------|--------|------|-------------|--------|
| 13 | **页面功能点** | 每个页面涉及的功能名称 | 流水线列表页：创建流水线、编辑流水线、删除流水线、手动触发、查看日志、复制配置 | 必须 |
| 14 | **页面布局** | 页面的分区名称 | 应用详情页：顶部信息栏、导航标签（概览/部署/监控/配置）、左侧环境列表、右侧主内容区 | 必须 |
| 15 | **功能描述** | 功能点的详细描述（入口、数据来源等） | 「手动触发部署」入口：① 流水线详情页右上角按钮 ② 应用列表页操作列下拉菜单 | 必须 |
| 16 | **约束条件** | 页面操作的约束条件 | 删除环境需满足：① 该环境下无运行中的 Pod ② 非生产环境 ③ 操作人具有「环境管理」权限 | 必须 |
| 17 | **异常处理** | 输入、导入错误等异常情况 | 导入 YAML 配置失败时：① 显示具体错误行号和原因 ② 提供「下载修正模板」按钮 ③ 保留已填写内容不丢失 | 必须 |
| 18 | **特例情况** | 空状态、无数据、数据边界情况 | ① 新建应用时：引导用户「创建第一条流水线」② 无构建历史时：显示「暂无构建记录」占位图 | 建议 |

### 3.5 界面元素规范

| 序号 | 内容项 | 说明 | DevOps 示例 |
|------|--------|------|-------------|
| 19 | **页面元素** | 页面包含的元素清单 | 流水线执行页：流水线名称、执行状态标签、阶段进度条、构建日志折叠面板、制品下载链接、执行耗时 |
| 20 | **控件类型** | 交互控件的具体类型 | 环境选择：`NSwitch` 开关控件；部署方式：`NRadioGroup` 单选组（滚动部署/蓝绿部署/金丝雀部署）；镜像版本：`NSelect` 可搜索下拉框 |
| 21 | **文案规范** | 页面各状态下的文案 | 构建中：「正在构建（预计剩余 3 分钟）」；构建失败：「构建失败，请检查代码后重试（查看错误日志）」 |
| 22 | **默认值** | 各控件的默认状态值 | 新建流水线时：触发方式默认「代码推送」，分支规则默认 `.*`（匹配所有分支），通知渠道默认「关闭」 |
| 23 | **可选项** | 下拉框、单选、多选的数据源定义 | 部署目标环境选项：① 开发环境 ② 测试环境 ③ 预发布环境 ④ 生产环境（需二次确认） |
| 24 | **交互方式** | 操作方式和动效 | 查看构建日志：点击「查看日志」按钮 → 底部滑出日志面板（动画 300ms 淡入）→ 自动滚动至最新日志 |
| 25 | **动效规范** | 交互动效详细说明 | 流水线执行状态变化：状态标签从「排队中」（灰色）变为「执行中」（蓝色旋转动画），最后变为「成功」（绿色勾选，200ms 弹跳效果） |

#### DevOps 术语表示例

| 术语 | 英文全称 | 定义说明 |
|------|----------|----------|
| 流水线 | Pipeline | 由一系列阶段（Stage）组成的自动化工作流，用于完成代码构建、测试、部署等任务 |
| 制品 | Artifact | 构建过程产生的可交付物，如 Docker 镜像、JAR 包、静态文件等 |
| 环境 | Environment | 应用部署的运行时环境，通常包括开发环境（Dev）、测试环境（Test）、预发布环境（Staging）、生产环境（Prod） |
| 蓝绿部署 | Blue-Green Deployment | 一种零停机部署策略，同时维护两套生产环境（蓝/绿），通过流量切换实现无缝更新 |
| 金丝雀发布 | Canary Release | 渐进式发布策略，先将新版本部署到少量实例，验证无误后再逐步扩大流量比例 |
| 命名空间 | Namespace | Kubernetes 中用于资源隔离的逻辑分区，不同环境的应用通常部署在不同命名空间下 |
| 配置中心 | Config Center | 集中管理应用配置的模块，支持环境变量、配置文件、密钥等配置的版本管理和动态下发 |

## 四、功能描述规范

### 4.1 描述原则

撰写功能描述时，请遵循以下原则：

#### 反面示例 vs 正面示例

| 原则 | ❌ 反面示例 | ✅ 正面示例 |
|------|-------------|-------------|
| **不要使用"等等"** | 流水线支持多种触发方式，包括代码推送、定时触发等等 | 流水线支持 4 种触发方式：① 代码推送 ② 定时触发 ③ 手动触发 ④ Webhook 触发 |
| **避免使用"与线上保持一致"** | 环境变量的导入导出功能与线上保持一致 | 环境变量导入导出功能与「应用配置中心」模块保持一致（支持 JSON/YAML/Env 三种格式） |
| **能用量词的不用形容词** | 支持多个构建节点并行执行任务 | 最多支持 **10 个**构建节点并行执行，每个节点可配置 **2-8 核 CPU** 和 **4-32 GB 内存** |
| **能用名词的不用代词** | 当用户点击它时，系统会将其状态更新 | 当用户点击「立即部署」按钮时，系统将部署单状态从「待部署」更新为「部署中」 |
| **能用表格的不用大段文字** | 环境配置页面包含很多字段，比如环境名称、环境标识、部署集群、命名空间、资源配额、访问域名等等，每个字段都有各自的校验规则和输入限制... | 见下方「环境配置字段说明」表格 |

#### 环境配置字段说明（示例）

| 字段名称 | 字段标识 | 控件类型 | 必填 | 校验规则 | 默认值 |
|----------|----------|----------|------|----------|--------|
| 环境名称 | name | 文本输入框 | 是 | 2-20 个字符，支持中文、字母、数字、下划线 | - |
| 环境标识 | code | 文本输入框 | 是 | 2-20 个字符，仅支持小写字母、数字、中划线 | - |
| 部署集群 | cluster | 下拉选择框 | 是 | 从已接入的 K8s 集群中选择 | 默认集群 |
| 命名空间 | namespace | 文本输入框 | 否 | 符合 K8s 命名规范（小写字母、数字、中划线） | 环境标识 |
| 资源配额 | quota | 资源配置器 | 否 | CPU: 1-64 核，内存: 2-256 GB | CPU: 4 核，内存: 8 GB |
| 访问域名 | domain | 文本输入框 | 否 | 符合域名规范，支持通配符 | {环境标识}.{应用标识}.example.com |

### 4.2 功能描述六要素

每个功能描述应包含以下要素：

```
1. 对象        - 功能针对什么对象
2. 触发动作    - 用户执行什么操作
3. 触发时机    - 在什么时机触发
4. 触发条件    - 需要满足什么条件
5. 约束条件    - 有什么限制规则
6. 数据变化    - 触发后数据如何变化
7. 文案展示    - 显示什么文案
```

#### DevOps 场景示例：自动部署流水线

**❌ 不规范描述：**
> 代码提交后自动部署到测试环境。

**✅ 规范描述：**

| 要素 | 具体内容 |
|------|----------|
| **对象** | 已配置 Webhook 的 Git 仓库 |
| **触发动作** | 开发者向 `develop` 分支推送代码 |
| **触发时机** | 代码推送完成后 |
| **触发条件** | ① 仓库已关联应用 ② 分支匹配规则 `develop` ③ 该应用在测试环境已启用自动部署 |
| **约束条件** | ① 同一应用的部署任务需排队执行，不可并行 ② 构建时间超过 30 分钟自动失败 ③ 代码扫描存在 Critical 级漏洞时阻止部署 |
| **数据变化** | ① 部署状态从「未部署」变为「部署中」 ② 构建日志实时写入 ③ 部署成功后版本号更新 |
| **文案展示** | 部署中："正在部署 v1.2.3 → 测试环境"<br>成功："部署成功（耗时 4m 32s）"<br>失败："部署失败：构建超时（查看日志）" |

#### 更多 DevOps 场景示例

**示例 1：制品版本保留策略**

> **对象**：应用构建产生的 Docker 镜像<br>
> **触发动作**：系统自动执行（每日凌晨 2 点）<br>
> **触发时机**：定时任务触发<br>
> **触发条件**：镜像数量超过保留策略阈值<br>
> **约束条件**：① 最近 30 个成功构建版本必须保留 ② 最近 5 个失败版本必须保留 ③ 标记为「保留」的版本不参与清理<br>
> **数据变化**：超出策略的镜像从仓库删除，释放存储空间<br>
> **文案展示**：清理报告发送至管理员邮箱，包含「已清理 X 个镜像，释放 X GB 存储空间」

**示例 2：环境变量批量导入**

> **对象**：应用的环境变量配置<br>
> **触发动作**：用户在环境配置页点击「批量导入」按钮，上传 CSV 文件<br>
> **触发时机**：用户主动触发<br>
> **触发条件**：① 文件格式为 .csv ② 文件大小 ≤ 1MB ③ 变量名符合规范 `^[A-Z][A-Z0-9_]*$`<br>
> **约束条件**：① 单次最多导入 100 个变量 ② 同名变量值被覆盖需二次确认 ③ 敏感变量值（如 PASSWORD、SECRET）自动加密存储<br>
> **数据变化**：① 导入成功：变量列表新增/更新记录 ② 导入失败：生成错误报告，标注第 X 行第 Y 列格式错误<br>
> **文案展示**：成功：「成功导入 24 个环境变量」；失败：「导入失败：第 7 行变量名包含非法字符 '-'」

**示例 3：容器资源监控告警**

> **对象**：运行在 K8s 集群中的应用 Pod<br>
> **触发动作**：系统监控指标达到阈值<br>
> **触发时机**：实时检测（每 30 秒采集一次指标）<br>
> **触发条件**：CPU 使用率 ≥ 80% 持续 5 分钟，或内存使用率 ≥ 90% 持续 3 分钟<br>
> **约束条件**：① 同一 Pod 相同类型的告警 30 分钟内只发送一次 ② 已配置「免打扰时间」的应用在此期间不发送告警 ③ 告警升级：Critical 级告警同时通知值班组长<br>
> **数据变化**：告警记录写入数据库，关联到对应的应用和 Pod<br>
> **文案展示**：邮件标题「[告警] 应用订单服务 CPU 使用率过高」；内容包含：当前使用率 87%、建议扩容至 4 核、一键扩容按钮

## 五、常见痛点与改进建议

### 5.1 收到的反馈

基于团队反馈，当前 PRD 存在以下问题：

| 问题类型 | 具体反馈 |
|----------|----------|
| **阅读优先级** | "主要看原型和设计稿，文字一般不看" |
| **理解难度** | "确认需求是否和想象的一样" |
| **一致性** | "文档的文案和设计稿对不上，所以搞不懂哪是哪" |
| **冗余内容** | "感觉很多页面有的内容没必要写在文档上" |

### 5.2 改进建议

#### 通用改进建议

1. **提高可读性**：使用清晰的结构、表格和列表，减少大段文字
2. **保持一致**：确保 PRD 与原型、设计稿的文案完全一致
3. **精简内容**：去除冗余信息，聚焦核心功能点
4. **突出重点**：使用加粗、引用等格式突出关键信息
5. **建立索引**：提供清晰的目录结构，便于快速查找

#### DevOps PRD 专项建议

**针对流水线配置的 PRD 写作：**

- ✅ **使用 YAML 示例**：对于复杂的流水线配置，提供可直接复制的 YAML 代码示例

```yaml
# 示例：多阶段流水线配置
stages:
  - name: 代码编译
    tasks:
      - name: Maven 构建
        image: maven:3.8
        commands:
          - mvn clean package -DskipTests
  
  - name: 单元测试
    tasks:
      - name: 运行测试
        image: maven:3.8
        commands:
          - mvn test
    allow_failure: false  # 测试失败时阻断流水线
  
  - name: 镜像构建
    tasks:
      - name: 构建并推送镜像
        image: docker:latest
        commands:
          - docker build -t $IMAGE_TAG .
          - docker push $IMAGE_TAG
```

- ✅ **状态流转图**：对于涉及多状态变更的功能（如部署单状态机），提供状态流转图

## 七、完整示例：DevOps 产品 PRD 章节

以下是一个完整的「流水线配置管理」功能 PRD 章节示例：

### 7.1 功能概述

**用户故事**
作为开发工程师，我希望能够可视化的配置 CI/CD 流水线，以便快速搭建自动化构建部署流程，减少手动操作带来的错误。

**功能价值**
- **效率提升**：将平均 30 分钟的环境搭建时间缩短至 5 分钟
- **错误减少**：通过标准化配置模板，降低 80% 的配置错误
- **知识沉淀**：配置可复用、可分享，便于团队协作

**功能范围**
- ✅ 流水线 CRUD 操作
- ✅ 可视化编排（拖拽式配置）
- ✅ YAML 导入导出
- ✅ 配置模板库
- ✅ 版本管理与回滚
- ❌ 运行时调试（后续版本支持）

### 7.2 页面功能点

#### 7.2.1 流水线列表页

| 功能名称 | 功能说明 | 操作权限 |
|----------|----------|----------|
| 创建流水线 | 跳转至新建流水线向导 | 项目成员及以上 |
| 编辑流水线 | 进入可视化编排器编辑配置 | 创建者/管理员 |
| 删除流水线 | 软删除，保留历史记录 | 管理员 |
| 手动触发 | 立即执行一次流水线 | 项目成员及以上 |
| 查看日志 | 跳转至最近一次执行详情 | 项目成员及以上 |
| 复制配置 | 基于现有配置创建副本 | 项目成员及以上 |

#### 7.2.2 流水线编排页

**页面布局**
```
┌─────────────────────────────────────────────────────────────┐
│  [返回]  流水线名称                    [保存草稿] [发布]    │
```

### 7.3 功能详细描述

#### 功能 1：拖拽编排流水线

**功能描述**
用户通过拖拽左侧阶段/任务面板中的组件至画布区域，构建流水线执行流程。

**对象**
已创建但未发布的流水线配置

**触发动作**
鼠标拖拽组件从左侧面板至画布区域，或在画布区域内调整组件顺序

**触发条件**
- 流水线处于「编辑中」状态
- 当前用户具有编辑权限
- 画布区域未超过最大阶段限制（20 个阶段）

**约束条件**
1. **阶段顺序约束**
   - 「代码拉取」阶段必须位于第一个位置
   - 「部署发布」阶段必须位于最后一个位置
   - 不能存在循环依赖

2. **任务依赖约束**
   - 任务只能依赖于同阶段内的前置任务或上一阶段的任务
   - 并行任务数不超过 5 个

3. **资源限制**
   - 单个流水线最多 20 个阶段
   - 单个阶段最多 10 个任务
   - 配置总大小不超过 500KB

**数据变化**
- 画布实时保存草稿状态
- 拖拽操作触发自动保存（防抖 3 秒）
- 发布时生成版本号（语义化版本 v1.0.0）

**文案展示**
- 保存成功：「配置已自动保存（12:34:56）」
- 校验失败：「配置校验失败：第 3 阶段缺少执行镜像（查看详情）」
- 发布成功：「流水线 v1.0.0 已发布，共包含 4 个阶段、8 个任务」

#### 功能 2：YAML 导入导出

**导入功能**

| 属性 | 说明 |
|------|------|
| **入口** | ① 列表页「导入」按钮 ② 编排页「导入 YAML」按钮 |
| **支持格式** | YAML、JSON（自动识别） |
| **文件大小限制** | ≤ 500KB |
| **校验规则** | ① 语法格式正确 ② 必填字段完整 ③ 引用的镜像仓库可访问 |

**导入错误处理**

```yaml
# 示例：导入失败的错误提示
错误类型: 配置校验失败
失败原因:
  - 第 15 行: stages[1].tasks[0].image 字段缺失
  - 第 28 行: stages[2].parallel 值无效，期望 boolean 类型
建议操作:
  1. 下载修正后的模板
  2. 参考错误位置修改后重新上传
  3. 或使用可视化编辑器手动配置
```

**导出功能**
- 支持导出当前版本或历史任一版本
- 导出文件命名格式：`{流水线名称}_v{版本号}_{日期}.yaml`

### 7.4 异常处理

| 异常场景 | 触发条件 | 处理方式 | 文案提示 |
|----------|----------|----------|----------|
| 配置丢失 | 用户编辑过程中刷新页面或意外关闭 | 自动恢复最近一次自动保存的草稿 | 「已恢复未保存的配置（2 分钟前）」 |
| 并发冲突 | 多人同时编辑同一条流水线 | 后保存者需选择「覆盖」或「另存为新版本」 | 「该流水线已被其他用户修改，请选择操作方式」 |
| 资源不足 | 配置的构建资源超出集群配额 | 保存时校验并提示，允许保存但不允许执行 | 「警告：配置的 8 核 CPU 超出集群可用资源（剩余 4 核）」 |
| 镜像不存在 | 引用的基础镜像在仓库中不存在 | 发布前校验，提供「去配置镜像仓库」入口 | 「镜像 nginx:1.19 不存在，请检查镜像标签或配置仓库访问权限」 |

### 7.5 特例情况

**空状态**
- 新建流水线首次进入编排页：显示引导遮罩，提示「从左侧拖拽阶段开始配置」
- 无历史版本时：「版本管理」按钮置灰，hover 提示「发布后可在版本管理中查看历史版本」

**边界情况**
- 配置内容过长：YAML 编辑器启用虚拟滚动，支持 10 万行代码流畅编辑
- 网络异常：自动保存失败时，显示「网络异常，配置将在恢复后自动保存」并本地缓存
